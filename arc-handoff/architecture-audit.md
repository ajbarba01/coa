# coa architecture audit — professionalization workstream source document

This is the source document for the professionalization workstream of the overnight autonomous
improvement arc. It is a faithful condensation of a 6-dimension architecture audit of the coa
codebase — dimensions: **layering, console-state, core-shape, error-honesty, test-quality,
simplicity** — generated **2026-08-07**, with every finding adversarially verified (each carries a
verdict; scope corrections from verification are reproduced verbatim and must be honored by the
executor). Result: **35 findings confirmed, 2 rejected**. Of the confirmed findings, **14 are
charter-worthy** and **21 are non-charter**. Fix sketches are reproduced verbatim from the audit —
they name reference projects and invariants the executor needs. All file paths and line numbers are
as written by the auditors.

## 1. Charter-worthy findings

### Layering

#### No rule encodes the backend-construction seam at package granularity — nothing forbids packages other than apps/cli from importing @coa/adapter-* or @coa/loop-driver (blast radius of KNOWN violation #1)

- **Severity:** structural
- **Packages touched:** packages/core, packages/spi, packages/loop-driver, apps/cli, root config

**Evidence.** `.dependency-cruiser.cjs` `backend-isolation` only forbids importing the raw SDK (`node_modules/(@anthropic-ai|@ai-sdk)/`) from outside adapter-claude-sdk; there is no rule about the workspace packages `@coa/adapter-claude-sdk`, `@coa/adapter-deepseek`, `@coa/adapter-longcat`, or `@coa/loop-driver`. Blast radius of the known core→adapter violation, mapped: (a) packages/core/package.json declares @coa/adapter-claude-sdk and @coa/adapter-deepseek as production dependencies; (b) packages/core/src/session/daemon.ts:17 imports `makeDeepSeekComplete` (web summarizer, composed at buildFetchSummarizer, daemon.ts ~:466-482) and :33 imports `managedLoginDir, probeAuthStatus, spawnLogin, extractOauthUrl` (Claude login plumbing); (c) packages/core/src/workbench/web/summarizer.ts:1 imports `type CompleteFn, DriverMessage` from '@coa/loop-driver' — so removing the adapter imports alone still leaves core depending on loop-driver for one type; (d) the injection seam already exists and is bypassed: apps/cli/src/session-deps.ts + adapter-factory.js construct the main backend and hand it to core, and packages/core/src/auth/login-manager.ts:71 already defines a port-shaped interface (`dirFor(email) // managedLoginDir(home, email)`) proving the port pattern is in place; (e) apps/desktop/src/main/daemon.ts deliberately depends only on a minimal DaemonClient interface — the desktop side is clean.

**Fix sketch (verbatim).** When the known violation is fixed: define the login-plumbing and summarizer `complete()` capability ports in @coa/spi (packages/spi/src/runtime-adapter.ts is the existing seam; move/re-export CompleteFn + DriverMessage there or into @coa/shared next to backend-message.ts), inject the concrete implementations from apps/cli/src/session-deps.ts exactly like adapter-factory.js does for the main backend (goose/opencode model this: provider factories live only at the CLI composition root, core sees interfaces). Then lock it in with a cruiser rule: `from: { pathNot: '^(apps/cli|packages/adapter-)' }, to: { path: '^packages/(adapter-|loop-driver)' }` (adapters may compose loop-driver; nothing else may). Invariants: D109 null-fallback still works with no backend present; M9 stays the one backend seam; core's package.json loses all adapter deps.

**Scope correction (verbatim — the executor must honor these).** Minor: the core→loop-driver coupling at summarizer.ts:1 is a type-only import (erased at runtime), slightly lighter than the finding implies — though @coa/loop-driver is still a production dependency in core's package.json, so the claim effectively stands. Cited line range daemon.ts ~466-482 is actually 471-480. Otherwise accurately scoped.

### Console state

#### Monolithic whole-state replace + identity-selector subscribers re-renders the entire workbench on every stream flush and poll tick

- **Severity:** structural
- **Packages touched:** apps/desktop, packages/console-viewmodel

**Evidence.** console.ts (apps/desktop/src/renderer) holds one mutable `ConsoleState` in the startConsole closure; every mutation (each rAF flush of streamed frames at flushTurns console.ts:587-607, each poll delta console.ts:310-327, each settings/pill change) rebuilds the whole object and calls publishConsoleState, which is a documented full replace (shell/consoleStore.ts:14-16, `useConsoleState.setState(s, true)`). Eight components subscribe with the identity selector `useConsoleState((s) => s)`: shell/Workbench.tsx:112, shell/Center.tsx:140, shell/Work.tsx:23, shell/Nav.tsx:273, shell/Palette.tsx:24, shell/Settings.tsx:209, shell/NewSession.tsx:15, panels/AgentsPanel.tsx:1266 — so every publish re-renders every mounted surface. The compensating machinery admits the cost: Freeze/DeferredCanvas (shell/deferredMount.tsx:6-18, 'would otherwise re-render on every live publish… making the console slower with each visited surface'), WeakMap frame-identity caches (panels/ChatPanel.tsx:27-34), and Center.tsx SurfaceCanvas comment lines 117-120 ('that cost is the switching slowdown').

**Fix sketch (verbatim).** Split the one store into slices with selector subscriptions, VS Code model/view style: (a) a transcript model — Map<sessionId, TurnFrame[]> — that IS the store (see finding 2), emitting per-session; (b) session-list/run-status slice; (c) slow data slice (cap/flags/timeline); (d) ui slice (overrides, dismissals, notes); actions as a stable module-level object outside state (they are already closure-stable, console.ts:918-943). Components subscribe to the slice they render (Nav to flags, TabStrip to sessions+runStatus, ChatSurface to its session's frames) — Podman Desktop's event-stream panes are the reference: each pane owns a materialized list updated by events, no global replace. Invariants to keep: frame object identity across appends (appendTurns builds [...prev, ...new] — the WeakMap/MemoRow contract, ChatPanel.tsx:27-32 — becomes optional but harmless), the rAF coalescer (console.ts:581-616) survives as the write batcher into the transcript slice, and pushToViewFrames/reconcileStreaming/reloadToViewFrames (packages/console-viewmodel) survive unchanged as the pure model layer. Freeze, DeferredCanvas-for-warm-tabs, and TabStrip's optimistic `pending` selection (Center.tsx:246-262) become deletable once renders are slice-scoped.

**Scope correction (verbatim — the executor must honor these).** Three small overstatements. (a) Headline says re-renders 'on every poll tick': refresh() at console.ts:316-324 explicitly skips the replace and publish when the 2s poll returns data equal to last time, so only changed ticks publish (the evidence body's 'each poll delta' is the accurate phrasing). (b) 'every publish re-renders every mounted surface': hidden kept-alive surfaces are shielded by Freeze (deferredMount.tsx:11-18 skips the frozen subtree), so strictly every publish re-renders the eight subscriber components plus the entire ACTIVE surface subtree — hidden surfaces are protected, but only by the compensating machinery the finding proposes to delete. (c) flushTurns publishes only when the active session has pending frames (activeValue guard, console.ts:600-606); background-session streaming reconciles buffers without triggering a publish. Also note this finding is largely the render-side blast radius of KNOWN issue (2) (poll-and-replace store → push-based store); it adds real specifics (identity selectors, slice boundaries, which machinery becomes deletable) but should be folded into that fix rather than treated as an independent work item.

#### Transcript truth is triplicated: a controller closure Map, a single-slot store field, and ChatPanel module-level Maps

- **Severity:** structural
- **Packages touched:** apps/desktop

**Evidence.** Three parallel caches of the same frames: (1) `turnsBySession` — a Map inside the startConsole closure, console.ts:573 — the only complete copy, invisible to React; (2) `state.data.turns` — a single Remote<TurnFrame[]> slot for ONLY the active session (panels/state.ts:37), swapped wholesale on every tab switch; (3) `framesBySession`/`nonceBySession` — module-scope Maps in panels/ChatPanel.tsx:16-20 that mirror the last frames each tab rendered so hidden tabs can keep DOM. Consequence: a background session streaming into (1) never reaches its hidden tab, which renders the stale snapshot in (3) until reactivation; the module Maps are never evicted on session delete (leak + stale reopen) and persist across StrictMode remounts/tests.

**Fix sketch (verbatim).** One store-owned per-session transcript map (the transcript slice of finding 1) becomes the single source: appendTurns/flushTurns write to it, ChatPanel's keepAlive tabs subscribe to their own sessionId's entry (so hidden-but-open tabs stay live, which is exactly the maintainer's 'fully materialized open tabs' requirement), and `data.turns` plus both module Maps are deleted. Eviction = tab close / session delete. Reference: VS Code's TextModel registry — models keyed by URI, owned centrally, views attach/detach; Podman Desktop keeps per-resource event-fed stores the panes select from. Invariant: reconcileStreaming's delta-fold/settle-replace contract (console-viewmodel/src/streaming.ts) and stable frame identity for MemoRow must survive the move.

**Scope correction (verbatim — the executor must honor these).** Minor overstatement: the stale snapshot in the module Maps is never user-visible while hidden (the tab is display:none and re-renders from the live vm the instant it becomes active, seeded from turnsBySession via openSession), so the consequence is architectural staleness/incompatibility with fully-materialized tabs plus a leak — not wrong content actually shown to the user.

#### openSession refires a full transcript reload on every tab switch and overwrites the live buffer — a mid-run frame-loss race the codebase already patches around

- **Severity:** significant
- **Packages touched:** apps/desktop

**Evidence.** console.ts:511-537: every selectSession (wired to tab clicks, keyboard cycling, the palette — none check run status) calls bridge.reloadConversation and then `turnsBySession.set(id, reloadToViewFrames(loaded.value))` unconditionally — frames flushed into the live buffer between the reload request and its response are discarded (only still-pending rAF deltas survive, reconciled onto the reloaded base). ChatPanel.tsx:563-569 documents the blast radius verbatim: 'a wholesale replacement of a session's frame array is reachable WHILE a turn is still running… its mid-run reload REPLACES the frames array outright' — the count-based pending-steer matching machinery (ChatPanel.tsx:539-570) exists specifically to survive this. Separately, materialization is activation-lazy: openTab (shell/store.ts:151) only adds the id to the strip; a never-visited open tab shows DeferredCanvas's spinner and blocks on the reload round trip on first click — violating 'open chat tabs fully materialized in memory, instantly scrollable'.

**Fix sketch (verbatim).** Make reload a cold-hydration path, not a switch path: (a) openTab (and boot-time tab restore) immediately prefetches reloadConversation + subscribeSession for every open tab, populating the store transcript map so activation is a pure display swap; (b) a warm, subscribed session skips reload entirely on selection — the push stream is authoritative once subscribed; (c) when a reload IS needed (cold open, resubscribe after daemon restart), merge by frame id against the live buffer instead of Map.set-overwrite. This is Podman Desktop's pattern (initial list fetch once, then event stream keeps it current). The count-based steer-pin matching can then be simplified back toward id matching. Invariant: live-vs-reload frame equivalence (docs/adr/0010/0013 — reload folds the same settled frames the stream delivered).

**Scope correction (verbatim — the executor must honor these).** Slightly overstated as data loss: the drop is view-layer only — the durable log is untouched, settled streaming text self-heals when its settled frame lands (appendStreamingFrame replaces/appends), and the next reload restores any dropped settled frame. The lasting loss window for settled frames is one rAF inside a local IPC round trip (narrow, though hit on every tab switch during streaming); the reliably user-visible symptom is the mid-stream partial-text wipe. Also the lazy-tab-materialization half overlaps KNOWN item (2) (poll-and-replace store / fully-materialized-tabs requirement) — it is blast-radius mapping of a known issue, not a new defect.

#### cap/flags/timeline ride a 2s JSON.stringify poll while a typed daemon push channel already exists

- **Severity:** significant
- **Packages touched:** apps/desktop, packages/shared

**Evidence.** App.tsx:13,93-96 — POLL_MS=2000 setInterval → controller.refresh(); console.ts:246-262 — remoteEqual is `JSON.stringify(a) === JSON.stringify(b)` over each Remote, run every tick (O(state) serialization ×3 every 2s forever); console.ts:310-327 replaces the whole ConsoleState when any of the three changed, republishing to every identity subscriber. Meanwhile packages/shared/src/push.ts already defines the server→client push wire (turn frames, status, deny) and the renderer already consumes it (console.ts:763-793 onPush) — the transport for pushing cap/flag/timeline deltas exists; only the event kinds don't.

**Fix sketch (verbatim).** Extend the push union in packages/shared/src/push.ts with cap/flags/timeline change events emitted by the daemon (M8 owns emission policy; the spine M1 already produces change events these can ride), and have the renderer write them into a slow-data slice — deleting the interval, remoteEqual, and refresh() from the critical path. If daemon-side emission is out of scope for the arc, the floor fix is keeping the poll but writing results into the dedicated slice so a tick never touches transcript subscribers. Reference: Podman Desktop pushes resource-change events from the main process instead of renderer polling; VS Code's extension-host model events likewise.

**Scope correction (verbatim — the executor must honor these).** Two corrections. (1) "only the event kinds don't exist" is wrong for cap and flags: pushSchema already defines `flag`, `drift`, and `cost` kinds (cost carries spent/remaining/capHit — exactly the cap data), but no daemon code emits them and the renderer's onPush ignores them; only timeline/checkpoints needs a genuinely new wire kind. The fix is daemon emission + renderer consumption of mostly-existing kinds, less schema work than stated. (2) The finding overlaps KNOWN issue 2 (poll-and-replace store) — it is the concrete blast-radius mechanism of that known item rather than a fully independent finding, though it adds real new detail (dormant push kinds, exact poll path). Minor: the per-tick O(state) stringify covers only the three cap/flags/timeline Remotes, not the whole ConsoleState.

### Core shape

#### session-handlers.ts is a god-module: RPC surface + both turn-drive strategies + persistence + stream/delivery machinery in one 1411-line closure

- **Severity:** structural
- **Packages touched:** packages/core

**Evidence.** packages/core/src/session/session-handlers.ts (1411 lines; its test file session-handlers.test.ts is 3150 lines — the largest file in the package). One exported function, buildSessionHandlers (line 410), contains as NESTED closures: the RPC verb map (createSession/closeSession/subscribeSession/interruptSession/steerSession/recompilePrompt, lines 1294-1410), the per-turn drive strategy (runPerTurn, 634-792), the entire held-open SDK drive strategy (makeRunTurn 805-863, establishHeldQuery 873-1125, continueHeldQuery 1133-1165, settleHeldQuery 1176-1218), the persistence prelude (prepareTurnPersistence 492-578, buildPersistenceHooks 586-624), child-spawn dispatch (startChild, 1224-1292), and parent-notify (notifyParentIfChild, 443-464). Module-level helpers StreamAccumulator (240-299) and DeliveryRecorder (312-356) are also defined here. The two strategies duplicate the record/emit/persist closure almost verbatim (runPerTurn 669-703 vs establishHeldQuery 959-1022) with subtle divergences (only held-open checks query.stopped and counts boundaries).

**Fix sketch (verbatim).** Split along the seams the code already names: (a) turn-drive strategies become session-scoped driver modules (per-turn-driver.ts, held-open-driver.ts) sharing one extracted frame-recorder (StreamAccumulator + DeliveryRecorder + the emit/persist closure, which differs only by seq-box and started-handle — inject those two); (b) turn persistence (prepareTurnPersistence/buildPersistenceHooks/prompt-freeze glue) becomes turn-persistence.ts; (c) session-handlers.ts shrinks to the thin verb→domain map. Reference shape: opencode keeps server routes one-line thin (packages/opencode/src/server) and puts all session business logic in a session/ domain namespace (session/index.ts, session/prompt); OpenHands likewise isolates the drive loop in AgentController, separate from the server layer. Invariants that must survive: SC-1 (interrupt never renders as error — the `interrupted` guards at lines 761-766, 780, 1195), the delivery-legality gate having exactly one writer (docs/adr/0031, the DeliveryRecorder comment at 301-311), and deltas never persisted (docs/adr/0013).

**Scope correction (verbatim — the executor must honor these).** Minor: the module exports deriveTitle plus two types in addition to buildSessionHandlers, so "one exported function" slightly overstates the module's single-export shape; and the nesting has an unstated cause the fix must handle — the closures share per-connection state (emit, turnMeta, subscribedSessions, unsubscribers) that an extraction must thread explicitly, which the proposed injection-based fix already accommodates. Otherwise accurately scoped.

#### Session-lifetime state and daemon-wide spawn dispatch are owned by per-RPC-connection closures, patched over with a last-writer-wins holder and a WeakMap side channel

- **Severity:** structural
- **Packages touched:** packages/core, apps/cli

**Evidence.** packages/core/src/session/session-handlers.ts: buildSessionHandlers is constructed fresh per RPC connection, yet it builds (a) makeRunTurn (line 805) whose closure holds SESSION-lifetime state (the open HeldQuery, heldSeqBox, heldStarted, 807-813) — the drive loop for a live session is thus owned by whichever connection happened to found it; (b) the daemon's ONE startChild (1224-1292), reconciled by the comment at 400-403: 'The composition root captures whichever startChild fires last into a late-bound holder; every connection's version is behaviorally identical … so it doesn't matter which one ends up captured'; (c) turnMeta, a WeakMap<TurnRequest, TurnMeta> keyed by object identity (466) to smuggle role/subscribe/onReady past the TurnRequest shape. The doc comment at 106-114 concedes TurnRequest 'has no room for' these fields. spawnSupport.onStartChild (404-408) exists solely to ferry the closure out to the composition root.

**Fix sketch (verbatim).** Move turn-driving and spawn to daemon scope: LiveSessionRegistry (or a new SessionService owned by the daemon, constructed once in apps/cli) owns makeRunTurn/startChild and the ConversationStore; buildSessionHandlers per connection becomes pure translation (parse params, call service, subscribe sink) — which also deletes the WeakMap (TurnMeta fields become explicit service-call parameters) and the late-bound startChild holder. This is the same daemon-side singleton shape opencode uses (Session/SessionPrompt are server-global; an HTTP/SSE connection only subscribes to the bus) and OpenHands uses (one AgentController per session, owned by the session manager, never by a connection). Invariant to preserve: G4 reattach — a connection is a stateless subscriber; hydration on subscribe must still reflect true run-status (the onStart-deferred subscribe at 1302-1308). Note this restructuring is the natural prerequisite for the KNOWN push-based console store, since a daemon-owned session service is what a push channel must attach to.

**Scope correction (verbatim — the executor must honor these).** Slightly understated: the finding frames the per-connection WeakMap + founding-connection runTurn as a structural smell, but it is a latent live bug — a turn sent to an existing session over a different connection than the founder misses the turnMeta lookup, silently dropping the turn's role (config key / prompt assembly, spurious held-query teardown at line 835) and never firing that connection's deferred onStart subscribe. The 'behaviorally identical' comment at 400-403 is only true for startChild, not for makeRunTurn/turnMeta. Conversely, one nuance: for startChild alone, last-writer-wins is genuinely near-harmless (all captured deps are daemon-shared); the real severity concentrates in makeRunTurn/turnMeta ownership.

**Scope correction (verbatim — the executor must honor these).** Accurately scoped. Trivial nit: buildDaemonConsoleHandlers wires four home-dir stores (AccountsRegistry, ConsoleStateStore, WebConfigStore, KeyStateStore), not three.

#### The interrupt/steer/turn lifecycle is a hand-rolled state machine smeared across mutable flags and swapped closures in five files — the hardest code in the repo to change safely

- **Severity:** significant
- **Packages touched:** packages/core

**Evidence.** The 'is this turn stopped?' truth is distributed over: LiveSession.control.interrupted (live-session.ts 38-48), written/cleared at session-handlers.ts 728-730, 761-766, 775-780, 1050-1052, 1144-1145 ('the stale interrupted flag must not make this turn's settlement look like a user stop'), 1185, 1359-1367 (set then conditionally UNSET when the closure declines); HeldQuery's parallel flags stopped/terminated/pendingTurns/boundary (session-handlers.ts 186-211) with pendingTurns counted at 954, 1099, 1122, 1162 and decremented inside the record closure at 1004; the strategy-specific interrupt behavior installed via session.setInterruptClosure inside each strategy's onStart (736-742, 1077-1104) and interrogated via closeInterrupted (live-session.ts 113-121); plus the COA_DEBUG_STEER stderr tracer (95-104) that exists because 'only the real SDK can reveal' the ordering. Verifying that a stop cannot double-emit 'interrupted' requires reading session-handlers.ts, live-session.ts, live-registry.ts (cascade abort), run-live-session.ts, and delivery.ts together.

**Fix sketch (verbatim).** Reify the turn lifecycle as one explicit state object per driver (states: idle → running → stopping → settled; events: boundary, interrupt, steer, error), owned by the extracted driver module (see finding 1), so `interrupted`, `stopped`, `pendingTurns`, and the boundary Deferred become transitions of a single machine instead of flags mutated from six call sites. Reference: OpenHands models exactly this as the AgentState enum on AgentController with a single set_agent_state transition point; opencode centralizes abort in one SessionPrompt lock/abort path. Invariants: SC-1 (a user stop is never an error frame), the exactly-once 'interrupted' status emission, and the held-open query surviving a turn-level interrupt (docs/adr/0012).

**Scope correction (verbatim — the executor must honor these).** Mild overstatement on 'five files': run-live-session.ts is a 35-line neutral loop holding no interrupt state, and delivery.ts participates only via seal()/flushAtBoundary() ordering — the smear concentrates in session-handlers.ts + live-session.ts with live-registry.ts as the third writer. Mild understatement elsewhere: live-registry.ts #closeOne sets interrupted=true and calls controller.abort() directly, bypassing the strategy closure, so a cascade close of a held-open session takes the whole-query abort path the held-open closure exists to avoid — the flag writers have already diverged in behavior, strengthening the finding.

### Error honesty

#### A daemon crash/restart mid-turn permanently wedges the session as 'running' — spinner, steer-mode composer, and queued messages never recover

- **Severity:** structural
- **Packages touched:** apps/desktop, packages/core

**Evidence.** Renderer run state is push-only: apps/desktop/src/renderer/console.ts:771-778 is the ONLY place `runStatus[sessionId]` is deleted (a 'status' push with a terminal state), plus the local startSession-rejection handler (console.ts:882-884). `sendMessage` sets `runStatus[id] = {since}` optimistically (console.ts:804). If the daemon dies mid-turn, the terminal push never arrives. On daemon recovery, App.tsx:54-68 fires `hydrate()` (console.ts:978-984), which re-runs loadAccounts/loadModels/loadCatalogue/initAgents but never touches `runStatus` and never re-subscribes the active session (the initSessions guard skips it because sessions are 'ok' and activeSessionId is set). Even re-opening the session doesn't help: the fresh daemon has no live session, so `subscribeSession` returns `{subscribed:false}` with no hydration push (packages/core/src/session/session-handlers.ts:1333-1338), and the renderer discards both the result and any rejection (`void bridge.subscribeSession({id}).catch(() => {})`, console.ts:522). Stop is equally mute: `interruptSession` returns `{interrupted:false}` for an unknown session (session-handlers.ts:1358-1370) and the renderer ignores it (console.ts:713). Consequences fan out: Work.tsx:27, Palette.tsx:35/109, Center.tsx:351, Browser.tsx:128 and ChatPanel.tsx:376 all render 'running' off this map, and ChatPanel's queue release (ChatPanel.tsx:503-515) waits for a running→idle transition that never comes, so queued follow-ups are held forever.

**Fix sketch (verbatim).** Make the daemon the reconciliation authority on every (re)attach, the way VS Code's renderer reconciles with the extension-host/terminal process on reconnect and opencode's TUI re-reads server session state after a connection drop. Concretely: (a) treat `subscribeSession → {subscribed:false}` as an authoritative 'this session is not running' and clear `runStatus[id]`; (b) on the App.tsx `cameUp` transition (which always means the previous daemon connection died), clear the whole `runStatus` map before hydrate — a brand-new daemon connection cannot have running turns this renderer started; (c) surface `interruptSession → {interrupted:false}` (at minimum clear the pill) instead of `.catch(() => {})`-and-ignore. Invariants to keep: the pill must still be driven by daemon pushes during normal operation (ADR 0011), and a mid-use restart must not yank the user to another conversation (the existing initSessions guard).

**Scope correction (verbatim — the executor must honor these).** Minor: "permanently wedges" overstates slightly — runStatus is renderer-memory, so a manual window reload or app restart clears the stale pill (fresh state + reattach). No in-app action (re-opening the session, Stop, hydrate, the 2s poll) recovers, so the wedge is real for the lifetime of the renderer state. Also the consumer files live under shell/ (shell/Work.tsx etc.), not bare paths as cited; line numbers were correct.

#### The Usage surface presents fabricated, hard-coded spend/limits as live data for the user's real credentials

- **Severity:** structural
- **Packages touched:** apps/desktop, packages/core

**Evidence.** apps/desktop/src/renderer/panels/mockUsage.ts:103-137 defines `FIXTURES` keyed by credential LABEL ('worm', 'school', 'personal', 'ds') with invented per-day costs, token rates, and rate-limit percentages ('7-day 52%, Resets Fri 07:00'); `accountUsage()` (mockUsage.ts:154+) joins these fixtures against the REAL credentials hydrated from the daemon (`credentialsOf` from mockAuth.ts, which is live daemon data despite the filename — its header says 'LIVE from the daemon'). The surface is shipped and reachable: Nav routes 'usage' and Center.tsx:77-78 renders `<UsageSurface />`; UsagePanel.tsx:215-220 hydrates the live credential store then charts fixture numbers. So a real account whose label isn't a fixture key shows $0.00 forever, and one that happens to match shows invented dollars and limit bars — while the daemon actually owns a real ledger (Governance `capState`/`record`, packages/core/src/session/daemon.ts:132-134) that this surface never reads. The file's own header claims 'Honest degradation is the whole job here', which the fixture join contradicts.

**Fix sketch (verbatim).** Wire the surface to the real M7 ledger (capState / decision-log spend records already exposed over the console RPC handlers in packages/core/src/rpc/console-handlers.ts) and delete the fixture ledger, the way Cline and Codex CLI show only actually-metered per-request cost and render 'unknown' when the provider publishes no limits. Where the real data doesn't exist yet (per-day series, per-model split), render an explicit empty/unknown state — the file's own stated principle ('we never draw a bar we can't fill honestly'). Invariant: keep the honest-degradation copy (LIMITS_UNREADABLE, subscription = modelled cost labelling) — only the data source changes.
